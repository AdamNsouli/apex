# Routing policy

The policy optimizes a comparable model/effort cohort. It does not establish that a model is best at an arbitrary individual task. It names no model: every number it uses comes from the benchmark data, which is refreshed daily.

1. Respect manual hold, settings/environment pins, account backend and confirmed IDs. Keep native settings if any required evidence or current input-token count is unknown. Aliases that do not map to an exact known runtime model retain native settings.
2. Join AA variants by exact identity. Where you saved mappings for a model they are the whole truth for it. Otherwise the effort variants AA publishes for the model join automatically: slug `<id>-<level>`, with the highest level under the bare ID, accepted only when the level the record's own name states agrees. A variant benchmarked with a fallback option on joins this way only for a model whose access you confirmed, and stays marked as such. Effort support and context/output limits come from runtime capability flags. Missing capabilities, unmatched/new identities and unspecified benchmark effort on an effort-capable model are excluded. Discovery never grants account access: a model found on the account is unused until you confirm it (`/apex confirm-models`).
3. Choose the score index. The task's own index (general, coding, agentic coding or a domain index) is used only when the native pair and every compared pair have it. Otherwise general intelligence is used for all of them, so the pairs stay comparable; the receipt records the index actually used. Math uses general intelligence as a documented proxy. Only the same reported AA major.minor methodology version is compared. AA does not expose methodology patch version here.
4. Require sufficient input context capacity and matching thinking-capability profiles with the baseline. Risky, complex, ambiguous and twice-failing intents retain baseline raw score and never reduce effort. More than 72-hour-old data follows the same quality restriction. More than seven-day-old data stops switching.
5. Set a target from the local intent. A tier gives the share of the strongest compared score that the task deserves and how long a person will wait for it: quick 70% and 20 s (simple, low risk), everyday 88% and 60 s (ordinary), hard 92% and 120 s (complex or high risk), critical 97% and 240 s (complex and high risk, or failed twice). An unclear request keeps the everyday tier but, as in step 4, never falls below the native pair. Eco asks for 10 points less. The strongest compared score always meets the target. Pairs without a measured AA cost per task are not offered; if none has one, native settings are kept.
6. Among the pairs that meet the target and the wait limit (AA's median end-to-end seconds; a missing latency cannot show a pair is too slow), choose the lowest measured AA cost per task, then the higher score, then the lower latency, then the current pair. If none is within the wait limit, the limit is relaxed and the fastest acceptable pair wins. High Quality takes the highest score (cost, then speed, break ties) with no wait limit. Sports takes the fastest pair within 3% of the strongest score. This is an index-distance heuristic, not a success-probability or quality guarantee.
7. Model hysteresis normally waits two steps. A lower-score winner on a different model must pay back conservatively over five equal-context requests by at least 5% of the forecast upper bound; unknown costs prevent that downgrade. A lower-score winner on the same model is an effort change, which keeps the prompt cache, and needs no payback. Treating every candidate request as uncached avoids assuming an unavailable cache hit. It does not predict all actual provider cache charges.
8. Forecast input at the higher known input/cache-write unit price plus the model's discovered maximum output budget at AA prices. This forecast is an upper bound for the budget gate and the payback test. It does not rank pairs.
9. Changed requests on a confirmed direct API backend require explicit APEX credit consent. When consent is enabled, reserve the upper forecast before dispatch against the configured API-equivalent routing budget. Unknown observed costs retain their reservation. Budget exhaustion preserves native settings; it never claims to stop all account charges.

## Staying current

Once a day, while a signed-in session is open, APEX rediscovers the account's models and refetches the benchmark data, then rebuilds the joined catalogue, so the next request already uses the new scores, costs and models. It compares the new data with the old and records what changed: models that appeared on or left the account, new effort variants, and score, cost, price or speed changes for the models you confirmed. `/apex doctor` prints the record. A model that appeared is shown in the rail and browser for a week with the command to confirm it. Confirming is the one step APEX does not take for you: it cannot tell whether your plan includes a model, and a model outside your plan can spend credits.

## Receipts and costs

The receipt stores mode, revision, original/requested pair, task/risk, tier, the index used, reason, top ten ranked comparisons, response-reported model and observed token cost when all needed prices are known. Rejected runtime models are excluded for the current joined catalogue; a later verified refresh can rebuild it. No automatic retry is performed by APEX.

AA's benchmark USD/task is the average cost of its Intelligence Index evaluation, not the predicted cost of your prompt. APEX uses it only to compare efforts and models with each other. Request forecasts and observed API equivalents are separate. No subscription usage percentage or actual credit balance is fabricated.

Quality once changes only the captured preference for the next main dispatch. It preserves base mode and follows all steps above, including hysteresis, consent and budget checks. Consumption is atomic before forwarding; agents cannot claim it. A main dispatch consumes it even when a guard holds native settings. Restart/clear cancels an unused token. Receipts freeze the exact baseline/selected evidence, prices, methodology and fetch time; refresh cannot alter a historical explanation.
